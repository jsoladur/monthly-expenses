## [Unreleased]

### Added
- Profile settings screen (UC-04): display-only currency label (PRD C9, UC-15, §7.6). New `userId`-first mutator `updateCurrency(userId, currency, tx)` in `src/server/repositories/profile-settings.ts` writes ONLY `profile_settings.currency` + bumps `updated_at` — the `char(3)` column type is the DB-layer defense in depth behind the Zod `^[A-Z]{3}$` regex in `currencySchema`. New service `src/server/services/settings.ts` owns the domain rule (ISO 4217 alpha-3, otherwise `InvalidCurrencyError`) and verifies the tenant has an `app_user` row before the update so a missing profile row surfaces as `ProfileSettingsNotFoundError`. New server action `updateCurrencyAction` in `src/actions/settings.ts` follows the Zod-parse → `requireUserId()` → service → `revalidatePath('/[locale]/settings', 'page')` pattern (ARCH §5 rule 3) and revalidates BOTH the settings page AND `/[locale]` so the home surfaces the new label on next render. New display helper `formatMoney(cents, currency)` in `src/i18n/format.ts` returns `<sign><amount> <LABEL>` with exactly two fractional digits and no grouping separator (PRD C9: dot-decimal in BOTH locales, so display mirrors input); throws on non-integer cents or non-3-letter labels (ADR-5, ARCH §8). New settings screen at `/[locale]/settings` (screen 8) is an RSC shell that loads the row, renders a `formatMoney` preview block (positive / zero / negative sample amounts in the active currency so the user can see the change before saving), and hands off to a client `SettingsForm` that uses React 19 `useActionState` + a native `<select>` for the picker — successful save bumps `formKey` so the select's `defaultValue` re-reads from the freshly-revalidated `currentCurrency` prop, and the confirmation surfaces through an `aria-live="polite"` region. i18n bundles extended with `settings.currentLabel`, `settings.preview.*`, `settings.actions.save`, `settings.status.saved`; existing `validation.currencyInvalid` is reused for the keyed error. PRD §15 #15 + the 2-decimal formatting invariant for every amount-rendering slice covered by `tests/unit/format-money.test.ts` (8 cases including the full `numeric(14,2)` range and rejection of non-integer cents) and `tests/integration/settings.test.ts` (7 cases — EUR default, single-row update, no-other-money-row-touched, tenant isolation, unknown-user `ProfileSettingsNotFoundError`, invalid codes rejected, repeated updates keep the row count at 1). Playwright e2e `tests/e2e/settings.spec.ts` (chromium + mobile-safari) reuses the auth-bypass helper from UC-03 and asserts the EUR → USD label swap in both the preview block and the live DB row, plus the Spanish variant.
- Fixed/estimated templates catalog (UC-05): per-user catalog of `committed` and `estimated` templates that are CLONED into a new month exactly once at month creation (PRD C17, §6.3, §7.8). New `userId`-first repository `src/server/repositories/template.ts` (`listTemplates` / `listTemplatesByKind` / `listActiveTemplates` / `listActiveTemplatesByKind` / `findTemplateById` / `insertTemplate` / `updateTemplate` / `deactivateTemplate` / `reactivateTemplate`); the `listActive*` family is the clone-source query for UC-06 and EXCLUDES soft-deleted rows, while `listTemplatesForManagement` includes them so the user can scan history. New service `src/server/services/templates.ts` validates that the target category is an ACTIVE expense category (using `findCategoryById` from the category repo and reusing `CategoryNotFoundError`) and round-trips the amount string through `parseAmount` → integer cents → `formatCents` per ARCH §8 / ADR-5. Soft delete is `active=false, deleted_at=now()`; a double-deactivate is mapped to `TemplateAlreadyInactiveError` via the repo's `WHERE active = true` guard, and reactivate reverses it (also `TemplateAlreadyActiveError` on double-reactivate). Editing a template never rewrites month rows — verified by `tests/integration/templates.test.ts` #10 (snapshot of month money-row counts is unchanged around a full CRUD cycle). Server actions in `src/actions/templates.ts` follow the Zod-parse → `requireUserId()` → service → `revalidatePath('/[locale]/templates', 'page')` pattern (ARCH §5 rule 3) and translate domain errors into `TemplateActionError = "validation" | "incomeCategory" | "inactiveCategory" | "notFound" | "alreadyInactive" | "alreadyActive" | "amountFormat"`. The UI is a single screen at `/[locale]/templates` (screen 7) with a committed/estimated tablist, an `AddTemplateForm` that uses `useActionState` + the `AmountInput` component to enforce the wire format, and a `TemplateRow` that toggles into an inline edit mode and offers deactivate/reactivate. Inactive rows render with reduced opacity + an "Inactive" badge. The home page now links to `/<locale>/templates` (alongside categories and settings) so the screen is reachable from the app. The page also surfaces the PRD §19 clone copy ("Fixed and estimated lines are copied when the month is created. This month is independent after that.") as a muted banner — also added to `months.clone` for UC-06. PRD §15 #11 + #16 + #17 covered by `tests/integration/templates.test.ts` (13 cases — happy create, negative amount accepted, income category rejected, inactive category rejected, unknown category is `CategoryNotFoundError`, edit preserves month rows, soft delete hides from clone query but keeps management row, double-deactivate, reactivate restores clone visibility, double-reactivate, kind bucket isolation, two-tenant isolation, no physical DELETE on `template`); Playwright e2e `tests/e2e/templates.spec.ts` (chromium + mobile-safari) reuses the auth-bypass helper from UC-03 and walks the create → deactivate → reactivate happy path plus the Spanish variant.

### Changed
- Split `src/components/amount-input.ts` (helpers only) into `src/components/amount-input-helpers.ts` because the two-file split (`.tsx` + `.ts`) confuses the path resolver; `AmountInput` now lives unambiguously at `src/components/amount-input.tsx`. `AmountInput` also accepts an `id` prop so callers can link `<label htmlFor>` and target the underlying `<input>` from tests.

- Categories management (UC-03): per-user global catalogs of expense and income categories with soft-delete-only (PRD §13). New `userId`-first repository `src/server/repositories/category.ts` (`listCategories`, `listActiveCategories`, `findCategoryById`, `insertCategory`, `updateCategoryName`, `deactivateCategory`, `reactivateCategory` — every function filters by `user_id` per ARCH §5 rule 1; the deactivate/reactivate guards require `active = true/false` respectively so a double-deactivate is a no-op and surfaces as `CategoryAlreadyInactiveError`). New service `src/server/services/categories.ts` with named domain errors (`DuplicateCategoryNameError`, `CategoryNotFoundError`, `CategoryAlreadyInactiveError`, `CategoryAlreadyActiveError`); unique-name collision is caught by walking the Drizzle `cause` chain to Postgres SQLSTATE 23505 and matching `constraint_name === 'category_active_name_uk'` — so a future schema addition can't accidentally be mis-translated. New server actions `src/actions/categories.ts` (`createCategoryAction` / `renameCategoryAction` / `deactivateCategoryAction` / `reactivateCategoryAction`) follow the Zod-parse → `requireUserId()` → service → `revalidatePath('/[locale]/categories', 'page')` pattern (ARCH §5 rule 3) and read `x-next-intl-locale` from headers so unauthenticated callers land on a locale-prefixed sign-in URL. New management screen at `/[locale]/categories` (screens 5–6) with an expense/income tablist, an `AddCategoryForm` using React 19 `useActionState` to surface keyed validation errors, and a `CategoryRow` that toggles into an inline rename mode and offers deactivate / reactivate. Inactive rows render with reduced opacity and an "Inactive" badge so users can scan the catalog and re-enable old entries without confusing them with active ones (PRD §6.2 — history stays intact via the FK join). i18n bundles extended with `categories.tabs.*`, `categories.empty.*`, `categories.actions.*`, `categories.help`, `validation.duplicateCategoryName`, `validation.categoryNotFound`. Docker Compose `db` service now publishes 5432 to the host (`DB_PORT` override in `.env`) so local `pnpm test` can hit the integration database without rebuilding the runner image. PRD §15 #16 + #11-picker-prep covered by `tests/integration/categories.test.ts` (12 cases); Playwright e2e `tests/e2e/categories.spec.ts` (chromium + mobile-safari) bypasses the Google OAuth dance by seeding an `app_user` row and forging an Auth.js session cookie via `next-auth/jwt#encode` (`tests/e2e/_helpers/auth.ts`).

- i18n shell (UC-02): next-intl with the `[locale]` App Router segment, locales `en` (default) and `es`, `localePrefix: 'always'`, and locale resolution order `NEXT_LOCALE` cookie → `Accept-Language` → `en` (PRD C4). New `src/i18n/routing.ts` is the single source of truth for supported locales; `src/i18n/request.ts` resolves the request locale and lazy-loads the matching bundle; `src/i18n/navigation.ts` exposes locale-aware `<Link>` / `redirect` / `usePathname` / `useRouter`. Edge middleware in `src/middleware.ts` (matches everything except `/api/*`, `/_next/*`, `/_vercel/*`, and dotfiles) rewrites and persists the cookie; `pages.error = '/403'` keeps working because the middleware redirects to `/<locale>/403` for the user's active locale. `next.config.ts` wraps the build with `createNextIntlPlugin('./src/i18n/request.ts')` so the standalone output-tracer keeps the request config (otherwise runtime fails with "Couldn't find next-intl config file"). New client primitives: `src/components/language-switcher.tsx` (uses `<Link locale=…>` — the middleware persists the cookie on navigation) and `src/components/amount-input.tsx` + `src/components/amount-input.ts` (controlled input enforcing `^-?\d{1,12}\.\d{2}$` in both locales, with the classifier extracted so it's unit-testable; rejects `1234,56` regardless of locale per PRD C9). Locale-aware helpers in `src/i18n/format.ts` (`monthName`, `monthYear`, `shortDate`, `amountToParts`) so month names follow `Intl.DateTimeFormat` and are never hardcoded (PRD §11). Full `en.json` / `es.json` seeded with the reserved namespaces called out in the slice (`language`, `common`, `nav`, `validation`, `warnings`, `months`, `categories`, `templates`, `settings`, `pwa`) plus a parity test that fails the build when a key drifts between locales. Root layout now reads the `x-next-intl-locale` header (set by the middleware) so `<html lang>` reflects the active locale instead of always being `en`. Vitest suites cover the new helpers (`tests/unit/i18n-format.test.ts`, `tests/unit/amount-input.test.ts`, `tests/unit/i18n-messages.test.ts`) and Playwright e2e (`tests/e2e/i18n.spec.ts`) covers the four UC-02 acceptance criteria on Chromium + mobile-safari (browser `es` → Spanish shell, browser `fr` → English fallback, language switcher persistence across reloads, translated 403).

### Fixed
- Signed-in users landing on `/[locale]` were silently redirected back to `/[locale]/sign-in`, making the Google sign-in flow look broken. The home now renders a minimal signed-in confirmation (email + display name + sign-out) until UC-06 delivers the real month workspace.
- Auth.js `jwt` callback was reading the Google `sub` from `user.id`, which without an Auth.js DB adapter is a freshly-minted `crypto.randomUUID()` generated by `@auth/core`'s `handleLoginOrRegister` (see `node_modules/.pnpm/@auth+core@0.41.3/.../actions/callback/index.js:70-80`). The callback now reads the stable OAuth subject from `account.providerAccountId` (falling back to `profile.sub`), short-circuits when `token.userId` is already set, and the `session` callback writes the internal `app_user.id` onto `session.user.id` — so the home page (and every later repository call) sees the right tenant id.

### Added (UC-00 / UC-01)
- Google sign-in, allowlist & tenancy (UC-01): Auth.js v5 with the Google provider and an `ALLOWED_EMAILS` allowlist enforced in the `signIn` callback (trim + lowercase normalization), JWT session strategy carrying the internal `app_user.id` (resolved from `google_sub` in the `jwt` callback, exposed via the `next-auth` module augmentation in `src/types/next-auth.d.ts`). First-time sign-in provisions `app_user` + `profile_settings(currency='EUR')` atomically via the `upsertUserOnSignIn` service; denied users get no session and no DB row and land on `/[locale]/403` through `pages.error = '/403'`. New `requireUserId()` primitive in `src/server/auth/require-user-id.ts` (cached with `React.cache`) reads the session in the data-access layer and redirects to the locale-prefixed sign-in when absent, so every repository keeps `userId` first per PRD §5.1. `userId`-first repositories `src/server/repositories/user.ts` and `src/server/repositories/profile-settings.ts`. Locale-aware sign-in and 403 screens at `/[locale]/sign-in` and `/[locale]/403` render `auth.signIn.*` / `auth.forbidden.*` copy from `src/i18n/messages/{en,es}.json` (minimal `loadMessages` helper — UC-02 swaps this for the full next-intl routing setup). `server-only` dependency + Vitest stub so the marker package resolves in Node test runs. PRD scenarios #1 (allowlist hit/miss → 403) and #2 (two users isolated) covered by `tests/unit/allowlist.test.ts` and `tests/integration/auth.test.ts`.
