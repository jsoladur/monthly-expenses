# UC-02 — Internationalization shell (en/es)

> **Database:** not touched. Locale lives in a cookie, not in the DB (PRD §5.4).
> **PRD refs:** UC-03; C4; §11.
> **ARCH refs:** ADR-8 (next-intl); §7 (cookie rule).

## Goal

Every user-facing string in the app is keyed and available in English and Spanish, with locale resolution: persisted cookie → browser `Accept-Language` (only `en`/`es` honored) → `en` (PRD C4).

## Work

- Configure next-intl with the `[locale]` App Router segment; locales `en`, `es`; default `en`.
- `src/i18n/messages/en.json` + `es.json` — seed with the keys for what exists so far (sign-in, 403) and the reserved namespaces for later slices: `validation.*`, `warnings.pastMonth`, `warnings.overspend`, `months.*`, `categories.*`, `templates.*`, `settings.*`, `pwa.*` (PRD §11).
- Month names always come from the locale (`Intl.DateTimeFormat`), never hardcoded (PRD §11).
- Language switcher component (screen 9) that persists the `locale` cookie. The cookie is a UX convenience, never a security boundary (ARCH §7).
- Amount inputs stay dot-decimal `1234.56` in BOTH locales — do not localize the input format (PRD C9/§11).

## Acceptance criteria

- Browser `es` → Spanish shell; browser `fr` → English fallback.
- Switching language persists across reloads via the cookie.
- 403 and validation messages render translated.
- Amount input rejects `1234,56` and accepts `1234.56` regardless of locale.
